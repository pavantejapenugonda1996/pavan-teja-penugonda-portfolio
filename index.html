How I'd approach it

Whichever case it is, I approach it as a software engineer and as an AI engineer. As a software engineer I understand the requirement, design it simply, build it in small tested pieces, and make sure it holds up in production. As an AI engineer I make sure the models are grounded, evaluated, and explainable before anything goes live.

</>As a software engineer

  • Start with requirements. Gather the need with stakeholders, break it into user stories, and agree on acceptance criteria before writing code.
  • Profile, don't guess. Logging and distributed tracing show where the time goes, so effort goes to the biggest win first.
  • Small services, clear contracts. Each microservice has a defined API and can be developed, tested, scaled, and deployed independently.
  • Resilient by design. Async processing with timeouts, retries, and queues, plus idempotent, versioned pipelines.
  • Tests that guard quality. Unit, integration, and regression tests, with load tests as release gates.
  • Ship safely. CI/CD pipelines, feature flags, and rollback, with structured logs and traces so issues are fast to root-cause.

AIAs an AI engineer

  • Ground, don't guess. Retrieval first: models answer from retrieved evidence with citations, and "insufficient evidence" is a valid output.
  • Narrow skills over one giant prompt. Specialised, skill-based agents with structured outputs are easier to test, swap, and improve.
  • Don't trust the model alone. Pair LLM output with deterministic checks, and route low-confidence cases to a human with the reasoning attached.
  • Pick the metric by risk. Accuracy can hide missed risk, so I track recall, false-positive reduction, and citation correctness, using time-based splits to avoid leakage.
  • Evaluate on the hard cases with reviewer-labelled samples, not just clean data, before anything goes live.
  • Explain and guard. Confidence scores, feature drivers, schema-validated outputs, least-privilege MCP tools, and drift monitoring.

My problem-solving playbook

  1. UnderstandStart from the business problem, users, and risk, not the tool.
  2. DesignPick the simplest architecture that meets the need and can grow.
  3. Build smallShip thin vertical slices, with tests, so feedback comes early.
  4. EvaluateProve it on real data with the metrics that matter to the business.
  5. OperateMonitor, explain, and keep improving after launch.
